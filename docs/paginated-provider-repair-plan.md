# 分页 Provider 自动修复实施方案

## 背景与目标

Provider 切换后，分页 rollout 的 `session_meta` 首行长度可能发生变化。首行变化会使后继分支保存的 `history_base.end_byte_offset`、历史库中的 turn 起止偏移和 projection 游标失效；只修改 SQLite 的 Provider 字段会留下“元数据看似修复、正文边界仍错误”的半修复状态。

本阶段的目标是：在不重建、不拼接、不删除 JSONL 正文的前提下，安全重写目标逻辑会话的分页 Provider 元数据，并同步重算所有受影响的字节偏移。所有写入先在一致数据库副本和 rollout 副本上试写，通过后才写真实数据；失败时使用本次备份恢复。

## 执行顺序

1. **只读扫描**：读取唯一状态库、历史库和 sessions/archived_sessions 中的分页 rollout，建立全局物理分支索引。
2. **完整性规划**：验证唯一物理 ID、唯一末端、父分支存在、ordinal 连续、字节边界可解释；拒绝跨文件重复 ID、多个历史库和无法定位的 turn。
3. **偏移预测**：计算每个分支首行改写的字节增量，沿后代链更新 `history_base`，并映射 `thread_turns` 与 projection 的偏移。
4. **副本试写**：通过 SQLite Backup API 复制 state/history 数据库；复制 rollout 文件到唯一临时目录；在副本上执行 compare-and-swap 更新、首行改写和完整性检查。
5. **真实写入**：再次确认扫描结果未过期，创建包含 WAL 一致快照的备份；按旧值条件更新真实数据库，精确替换首行，正文哈希必须保持一致。
6. **收敛验收**：重新扫描目标线程，确认分页修复项消失、所有 SQLite 完整性检查通过；任一步失败都从本次备份恢复。
7. **客户端验收**：退出并重启 Codex 后检查原对话 ID、标题、项目归属、消息顺序、正文无遗漏无重复。工具只将“入口与偏移修复完成”作为自动验收结果，不冒充完成桌面端逐条读取验收。

## 安全边界

- 普通“备份并修复”按钮不执行分页首行改写；分页修复必须由用户在独立确认区域显式触发。
- 不修改会话正文、逻辑 ID、物理 ID、标题、项目归属、Provider 配置、OAuth/API Key 或 Codex.app。
- Codex 或 app-server 运行时拒绝写入；测试通过依赖注入运行状态检查，不杀进程。
- 状态库、历史库和 rollout 文件不是跨数据库原子事务，因此备份恢复是故障兜底；发布前必须覆盖失败回滚测试。
- 找不到唯一 `thread_history_*.sqlite`、跨文件物理 ID 重复、多个末端、缺父文件、非法 ordinal/边界或未知文件影响目标链时，保持只读并给出局部诊断。

## 测试与发布验收

- 单元测试：首行长度变化、后代 `history_base`、50 字节中间偏移、重复 ID、多历史库和错误边界。
- 端到端测试：WAL 快照、副本试写、真实 rollout/SQLite 同步更新、正文哈希、失败回滚和过期预览。
- 回归测试：普通 Provider 修复、入口修复、编辑替换、未知文件局部阻断与备份轮换。
- 发布前使用 macOS 26.5 SDK 跑完整 Swift 测试和 Release 构建，更新 README、中文/英文发布说明，并在真实副本上完成重启后的读取验收。

## 当前状态

方案先行，v1.5.0 的基础诊断与安全备份已发布；本方案对应的分页 Provider 第二阶段尚在实现和测试中。未通过全部验收前，不修改用户真实 Codex 数据，也不发布 v1.6.0。
